# 视频压缩性能与完整性修复

版本保持 3.0.6，本轮不制作部署包，不修改生产服务或数据库配置。

## 原因和修复

- 服务端原来固定使用 `medium`。现默认 `speed=fast` 对应 `veryfast`，保留 `speed=balanced` 对应原 `medium`；界面名称分别为“快速压缩”和“标准压缩”。两档均为 CRF 26、H.264/AAC、最长边 1920、最高 30fps。
- 排队原来可能一直等待接近总超时。现单并发最多等待 30 秒，繁忙明确失败；排队、复制和编码共用 9 分 30 秒任务预算。
- 服务端等待期间原来固定显示 45%。现区分真实上传、服务端处理、接收结果三个阶段，未提供编码进度时显示不确定状态和实际经过时间，不伪造编码百分比。
- 本地模式依赖 MediaRecorder 实时录制完整视频。体积无收益时原来最多重新编码两遍，现直接保留原文件；录制异常的有限兼容重试仍保留。
- 专业模式失败后停止并提供手动切换本地的入口，不自动追加整段实时录制。本地设置中明确提示至少接近视频时长，并要求保持前台。
- 原本在进度四舍五入到 99% 时结束录制，可能丢失长视频尾部。现等待 `ended`，并锁定处理中的原视频控制，重置播放速度为 1。
- WebM 未提供有限容器时长时显示“容器未提供时长”，不把 Infinity 格式化成 00:00。

## 本机真实性能对比

环境：Apple M1 Max，FFmpeg 8.1.2。素材为本地生成的 18 秒 1080p30 视频，含 AAC 音轨，源文件 55,895,443 B。两档交替、顺序各编码两次，耗时不包含独立解码验收。

| 编码档 | 平均耗时 | 输出体积 |
| --- | ---: | ---: |
| 原 medium | 3.152 秒 | 9,441,652 B |
| 默认 veryfast | 1.555 秒 | 8,670,974 B |

本合成片编码约快 2.03 倍；四份产物均通过 ffprobe 和完整解码，H.264/AAC、1920×1080、时长 18.005 秒。本例的体积和速度不能外推到所有视频或线上服务器，也未据此宣称两档画质相同。

可复现命令：

```bash
node scripts/benchmark-video-compression.mjs --report .runtime/logs/video-perf-20261029/benchmark.json
```

脚本默认删除大型中间视频；`--fixtures` 可额外生成用于浏览器上传的 3 秒小视频。没有新增依赖。

## 验证

- 前端 Vitest：78 文件、829 项通过，其中视频相关 3 文件、32 项。
- `npm run build:check`：类型检查、构建、6 个工具首个 HTML 预渲染通过；原有大分块提示仍存在。
- Go `go test ./...`：全部通过，包含速度白名单、multipart 透传、队列超时/取消/释放。
- `git diff --check`：通过。
- 实际本地浏览器：AVI 专业压缩、MP4 快速/标准压缩、真实下载、本地录制与取消均完成；320/375/768/1440px 无横向溢出，每页一个 H1。
- 实际下载 MP4：H.264/AAC、320×180、视频 3.000 秒，完整解码通过。
- 实际下载本地 WebM：VP9/Opus、320×180，容器未声明时长，但完整解码为 3.004 秒，音轨保留。
- 故障、未知下载长度、取消和迟到结果由单测覆盖。停止整个本地 API 的浏览器检查会先触发站点配置前置门禁，因此不把这次模拟计为“转码接口不可用分支”的浏览器验收。

## 范围限制

当前仍为同步附件接口，未实现实时编码进度或断线恢复的持久任务。没有验证 500MB、手机真机、Safari/Firefox、线上 CPU 或上传带宽。长视频仍可能超过同步接口的反代/HTTP 总时限；进一步扩展应采用独立任务与结果下载机制，并单独验证部署资源。
